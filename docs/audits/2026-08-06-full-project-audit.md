# Полный аудит Nemexia Raid Manager

Дата аудита: 2026-08-06  
Baseline: `a33632bc092ede70f7d6e6c4a819dd65b055bf1d` (`main`)  
Тип изменений: только документация, без изменения поведения программы.

## 1. Область аудита

Проверены:

- архитектура и границы модулей;
- сценарии подключения к браузеру и отправки флотов;
- расчёты очереди, времени, слотов и астероидов;
- импорт разведывательных и боевых отчётов;
- SQLite-схема, миграции, дедупликация и резервные копии;
- ручное сохранение страниц;

- тесты и отсутствие CI;
- безопасность локальных и репозиторных данных;
- структура, визуальная система и UX Tkinter-интерфейса;
- актуальность README и технических отчётов.

Аудит статический. Живые рейсы, реальная отправка флотов и Windows-сборка в рамках аудита не запускались.

## 2. Итоговая оценка

Проект уже решает реальную задачу и содержит заметное количество защитных механизмов. Сильные части — подтверждение исходной планеты, контроль CAPTCHA, использование фактического времени из игры, SQLite/WAL, дедупликация истории, резервные копии и консервативная остановка астероидного цикла при неопределённом результате.

При этом текущая зрелость проекта не соответствует риску автоматической отправки игровых действий. Основные причины:

1. успешность обычного рейда не требует фактического появления новой строки полёта;
2. обычная отправка считает занятыми только атакующие рейсы и может игнорировать другие миссии;
3. кнопка отправки принудительно разблокируется, обходя клиентскую валидацию игры;
4. приватные игровые страницы и реальные цели уже отслеживаются в публичном репозитории;
5. нет CI, единой системы тестов, зафиксированных зависимостей и защиты `main`;
6. формулы и README расходятся с фактическим поведением;
7. крупные монолитные файлы и runtime monkey patch усложняют безопасные изменения.

Общая оценка риска: **высокий для автоматической отправки**, **средний для ручного режима**, **низкий для просмотра и импорта данных**.

## 3. Приоритеты

### P0 — исправить до дальнейшего расширения автоматической отправки

#### P0.1. Обычный рейд считается успешным без подтверждённой строки полёта

`BrowserWorker._send_raid_once()` ищет новую строку в таблице полётов, но при её отсутствии всё равно возвращает успешный результат с `fleet_id=None`. Для астероидов аналогичная ситуация корректно вызывает `UnverifiedSendError`, а для обычных рейдов — нет.

Риск:

- ложная запись в истории;
- перевод элемента очереди в выполненный статус;
- повторная отправка той же цели;
- невозможность отличить реально принятый рейс от зависшего интерфейса.

Как исправить:

- сделать подтверждение новой строки обязательным и для обычных рейдов;
- при отсутствии строки возвращать отдельный `UnverifiedSendError`;
- не менять очередь и статистику цели до подтверждения;
- добавить ручную команду «Синхронизировать и разрешить неопределённую отправку».

#### P0.2. Свободные слоты обычных рейдов считаются только по атакам

`BrowserWorker.sync_flights()` фильтрует только миссию «Атака». Именно этот метод используется экраном рейдов, волной и автоотправкой для формулы:

`free_slots = max_slots - len(attack_flights)`.

Астероидные, транспортные, шпионские и другие активные миссии при этом могут не учитываться, хотя занимают игровые слоты.

Риск: программа пытается отправить больше флотов, чем разрешает игра.

Как исправить:

- единым источником занятых слотов сделать `sync_all_flights()`;
- отдельно получать `attack_flights` только для отображения и защиты от повторной атаки координаты;
- на дашборде показывать «занято всего» и разбивку по миссиям.

#### P0.3. Принудительное снятие `disabled` с кнопки отправки

Перед отправкой обычного рейда код выполняет `removeAttribute('disabled')`, если `#SendFleetButton` отключена.

Это обходит клиентскую валидацию игры: недостаток газа, неверная цель, отсутствие слота или иное блокирующее условие.

Как исправить:

- никогда не снимать `disabled` программно;
- считать отключённую кнопку валидной ошибкой состояния;
- сохранять видимые причины, DOM-состояние и диагностический снимок;
- повтор разрешать только для точно распознанной временной ошибки выбора кораблей.

#### P0.4. Ответ сервера принимается как успех без явного `pass == 1`

Код останавливается только при `pass == "0"`. Пустой, повреждённый или неожиданный ответ может попасть в ветку успеха.

Как исправить:

- успех признавать только при документированном положительном значении;
- неизвестный формат ответа классифицировать как `unverified`;
- сохранять ограниченный диагностический фрагмент ответа без секретов.

#### P0.5. Приватные игровые данные отслеживаются Git

В `main` находятся:

- `saved_pages/**/page.html`;
- `saved_pages/**/page.mhtml`;
- скриншоты;
- метаданные снимков;
- реальные координаты, имена игроков и энергия в `targets_seed.json`.

Сохранённые страницы могут содержать игровые ресурсы, координаты, внутренние ссылки, токены и данные сессии. Локальное удаление папки не удалит их из истории Git.

Как исправить отдельным security PR:

1. добавить `saved_pages/` в `.gitignore`;
2. удалить папку из индекса Git;
3. заменить `targets_seed.json` демонстрационным набором;
4. решить, требуется ли переписывание публичной истории;
5. после переписывания считать ранее опубликованные токены скомпрометированными;
6. запретить `git add -A` без проверки чувствительных путей.

### P1 — исправить следующим блоком

#### P1.1. Расчёт времени отправки синхронизированного рейса основан на допущении симметрии

Используется:

`sent_at = 2 * arrival_at - return_at`.

Формула корректна только при `round_trip = 2 * one_way`. Для разных модификаторов или миссий это необходимо подтвердить контрактом игры.

Как исправить:

- маркировать время как `inferred`;
- хранить исходные countdown-значения;
- использовать серверный timestamp/идентификатор, если он доступен в деталях флота;
- покрыть несимметричные примеры тестами.

#### P1.2. Временные зоны отчётов трактуются как UTC без доказательства

Парсер присваивает строкам времени `timezone.utc`, хотя сохранённая страница игры указывает серверное время UTC+04:00. Это может сдвигать возраст разведки и даты отчётов на четыре часа.

Как исправить:

- ввести явную `GAME_SERVER_TIMEZONE`;
- хранить время в UTC после корректного преобразования;
- отдельно хранить исходную строку;
- добавить тест UTC+04 → UTC → локальное отображение.

#### P1.3. Очередь использует старую разведку без ограничения возраста

Фактический фильтр очереди требует только наличие `last_spy_at` и металл выше порога. Параметр глубины отчётов ограничивает импорт страниц, но не запрещает старой записи участвовать в новом плане.

Риск: рейд строится по устаревшему количеству ресурсов.

Как исправить:

- добавить настройку `max_spy_age_hours`;
- исключать просроченные цели из автоматического плана;
- разрешить ручное включение с явным предупреждением;
- показывать возраст разведки цветом и текстом.

#### P1.4. Документированная формула рейтинга не совпадает с программой

В `Target` существуют формулы эффективности и score по энергии, времени и свежести. README также описывает такой рейтинг. Но текущий `ranked_targets()` сортирует цели только по металлу.

Это не обязательно ошибка продукта, но это ошибка контракта и мёртвый код.

Как исправить:

- выбрать один официальный алгоритм;
- удалить неиспользуемые формулы либо вернуть их как отдельный режим;
- отображать компоненты приоритета в UI;
- добавить golden tests на порядок целей.

#### P1.5. ZIP-импорт требует безопасной распаковки

Используется `ZipFile.extractall()` для выбранного пользователем архива.

Как исправить:

- проверять нормализованный путь каждого entry;
- запрещать абсолютные пути и `..`;
- ограничить суммарный распакованный размер и количество файлов;
- предпочтительно читать HTML непосредственно из архива.

#### P1.6. Парсинг чисел может склеить несколько значений

`_number()` удаляет все нецифровые символы. Если одна строка содержит несколько чисел, они превращаются в одно большое число.

Как исправить:

- привязать число к конкретной ячейке/классу;
- разрешать один формат числа;
- отклонять неоднозначные строки;
- добавить реальные HTML-fixtures разных версий интерфейса.

#### P1.7. Несколько вкладок Nemexia создают неоднозначность

Автоматизация выбирает первую подходящую вкладку `fleets.php`, а не обязательно активную или привязанную пользователем вкладку.

Как исправить:

- сохранять CDP target ID выбранной вкладки;
- показывать URL/заголовок привязанной вкладки;
- добавить кнопку «Привязать текущую вкладку»;
- при исчезновении target ID останавливать действие, а не переключаться молча.

#### P1.8. Runtime monkey patch стал частью production-пути

`app_entry.py` устанавливает `ship_retry_fix`, который заменяет методы `BrowserWorker` во время запуска. Это решило проблему малым патчем, но создаёт два варианта поведения: прямой запуск `app.py` и штатный запуск `app_entry.py`.

Как исправить:

- после подтверждения фикса перенести логику в `browser.py`;
- оставить один entry point;
- убрать monkey patch и отдельный совместимый слой;
- обновить self-test на точный текст игры.

#### P1.9. Встроенная проверка не запускает новые тесты

`install.bat` компилирует старый набор файлов и запускает только `self_test.py`. Он не проверяет:

- `app_entry.py`;
- `page_capture.py`;
- `ship_retry_fix.py`;
- `test_page_capture.py`;
- `test_ship_retry_fix.py`.

Как исправить:

- перейти на `python -m unittest discover` или pytest;
- запускать все тесты и компиляцию всех production-модулей;
- добавить GitHub Actions для Python 3.10 и 3.11 на Windows.

#### P1.10. Нет формальной схемы миграций

Миграции выполняются условными `ALTER TABLE` без версии схемы и rollback-плана.

Как исправить:

- использовать `PRAGMA user_version`;
- каждую миграцию делать идемпотентной и тестируемой;
- перед миграцией выполнять backup и `PRAGMA integrity_check`;
- добавить тест обновления нескольких старых схем.

### P2 — качество и сопровождаемость

#### P2.1. Монолитные модули

По размеру репозитория:

- `app.py` — около 120 КБ;
- `browser.py` — около 75 КБ;
- `storage.py` — около 40 КБ.

Как улучшить:

- `ui/` — shell, dashboard, queue, recon, asteroids, settings;
- `automation/` — connection, raids, flights, asteroids, messages;
- `domain/` — ranking, scheduling, formulas, policies;
- `persistence/` — schema, migrations, repositories;
- `diagnostics/` — screenshots, snapshots, structured events.

#### P2.2. Бизнес-логика находится в Tkinter callback-ах

Очередь, свободные слоты, подтверждения и сохранение состояния трудно тестировать без UI.

Как улучшить:

- вынести use-case сервисы;
- передавать зависимости через конструкторы;
- UI должен только собирать ввод, показывать результат и инициировать команды.

#### P2.3. Слишком широкое использование `Any` и строковых словарей

Результаты отправок передаются как `dict[str, Any]`, поэтому обязательные поля и состояния не проверяются типами.

Как улучшить:

- ввести `SendResult`, `SendVerification`, `CapacitySnapshot`, `ReportImportResult`;
- использовать enum для статусов;
- добавить mypy/pyright.

#### P2.4. Жёстко зашитые правила

В коде находятся:

- координаты защищённых целей;
- конкретная раса и ID кораблей;
- миссии по числовым ID;
- названия планет в сообщениях;
- диапазон систем 1–40;
- резерв кандидатов 5;
- лимит кандидатов 200.

Как улучшить:

- собрать явный `GameProfile`;
- валидировать расу и вселенную при подключении;
- отделить неизменяемые правила игры от пользовательских настроек.

#### P2.5. Мёртвые или устаревшие настройки

`wave_size`, `min_energy`, `repeat_minutes` и `Target.score()` либо не участвуют в текущем алгоритме, либо помечены UI как устаревшие.

Как улучшить:

- удалить после миграции либо вернуть как понятный режим;
- не хранить настройки без действующего поведения;
- документировать изменение алгоритма в changelog.

## 4. Что в проекте сделано хорошо

1. CAPTCHA не обходится, а приводит к остановке операции.
2. Для астероидов неопределённая отправка останавливает цикл во избежание дублей.
3. Координаты астероида корректно переходят через позицию 24 в следующую систему.
4. Время полёта и газ берутся из штатной формы игры, а не дублируются сомнительной собственной формулой.
5. Есть отдельный профиль браузера и подключение через CDP.
6. SQLite работает в WAL-режиме, использует индексы и дедупликацию.
7. Перед стартом создаётся backup, предусмотрено ограничение числа копий.
8. Защищённые координаты принудительно отключаются и исключаются из импортов.
9. Автоматический режим выключен по умолчанию и останавливается при ошибке.
10. Ручное сохранение страницы создаёт полезный комплект PNG + DOM HTML + MHTML + metadata.

## 5. Проверка документации

README сейчас требует пересборки. Основные расхождения:

- написано, что ресурсы не сохраняются и не влияют на рейтинг, хотя металл/минералы/газ хранятся, а металл является фактическим приоритетом;
- написано, что отправка подтверждается новой строкой, но обычный рейд может завершиться без неё;
- структура данных не включает локальную папку `saved_pages` рядом с приложением;
- не описаны чувствительность MHTML/HTML и запрет публикации;
- не описано ограничение на расу/ID кораблей;
- версия остаётся `1.1.0`, хотя поведение существенно менялось.

## 7. Критерии готовности безопасной версии

Автоматическую отправку можно считать достаточно защищённой, когда одновременно выполнено:

- все типы активных полётов участвуют в расчёте слотов;
- обычный рейд требует подтверждённую новую строку;
- отключённая кнопка никогда не разблокируется насильно;
- неизвестный ответ сервера не признаётся успехом;
- повтор выполняется только один раз для точной известной ошибки;
- очередь не меняется до подтверждения;
- сохранённые страницы исключены из Git;
- CI проходит на Windows/Python 3.10–3.11;
- есть contract fixtures реальных состояний страницы;
- README и реестр формул совпадают с кодом.

## 8. Ограничения аудита

Не проверены в живой среде:

- реальное поведение Nemexia при всех типах ошибок;
- корректность селекторов после будущего обновления игры;
- внешний вид на Windows при DPI 100%, 125%, 150% и 200%;
- поведение готового EXE и антивирусов;
- нагрузка на интерфейс при большой базе и длинной истории.

Эти проверки вынесены в remediation roadmap.
