# Решения владельца по аудиту

Дата решения: 2026-08-06  
Связанный аудит: [`2026-08-06-full-project-audit.md`](2026-08-06-full-project-audit.md)  
Baseline аудита: `a33632bc092ede70f7d6e6c4a819dd65b055bf1d`.

Этот документ фиксирует окончательный продуктовый scope после обсуждения аудита. Он имеет приоритет над первоначальными рекомендациями в полном аудите, UI/UX-аудите и remediation roadmap.

## 1. Принято в работу

### A1. Подтверждение обычного рейса

Обычный рейд нельзя считать успешно отправленным без подтверждённой новой строки полёта.

Требуемое поведение:

- положительный ответ сервера сам по себе недостаточен;
- должна появиться новая строка нужной миссии и нужной цели;
- при отсутствии строки результат получает состояние `unverified`;
- очередь, история и статистика цели не переводятся в успешное состояние;
- автоматическая повторная отправка при неопределённом результате запрещена.

### A2. Учёт всех активных полётов в слотах

Свободные слоты рассчитываются по всем активным миссиям, а не только по атакам.

Требуемое поведение:

- источник занятых слотов — `sync_all_flights()`;
- атаки можно фильтровать отдельно только для отображения и проверки повторной цели;
- перед каждой волной и автоматической отправкой выполняется актуальная синхронизация всех полётов.

### A3. Запрет принудительной разблокировки кнопки отправки

Если `#SendFleetButton` отключена самой игрой, бот не должен удалять атрибут `disabled`.

Требуемое поведение:

- остановить действие;
- получить доступное сообщение игры;
- сохранить диагностику;
- повтор разрешать только для отдельно подтверждённой ошибки выбора кораблей по существующему сценарию `Ок → Назад → один повтор`.

### A4. Ответ сервера принимается только при явном успехе

Успех разрешён только при ожидаемом положительном значении `pass`.

Требуемое поведение:

- `pass == 0` — отказ;
- ожидаемое положительное значение — переход к проверке строки полёта;
- пустой, повреждённый, HTML-ответ, отсутствие `pass` или неизвестное значение — `unverified`, а не успех;
- неизвестный ответ не должен инициировать автоматический повтор.

### A5. Проверка восстановления времени отправки

Формула восстановления времени отправки синхронизированного рейса должна быть проверена и оформлена как допущение, а не безусловно точное значение.

Текущая формула:

```text
sent_at = 2 × arrival_at − return_at
```

Требуемое поведение:

- проверить формулу на реальных рейсах и разных миссиях;
- различать точное и вычисленное время;
- вычисленное значение маркировать как `inferred`;
- при доступности использовать серверный timestamp или исходные countdown-значения.

### A6. Корректный часовой пояс отчётов

Время сообщений и отчётов нельзя без доказательства считать UTC.

Требуемое поведение:

- определить фактический часовой пояс сервера Nemexia;
- ввести явную настройку/константу часового пояса игры;
- преобразовывать время в UTC перед сохранением;
- хранить исходную строку времени для диагностики;
- добавить тест преобразования серверного времени.

### A7. Ограничение возраста разведки

Старая разведка не должна бесконтрольно участвовать в автоматическом плане.

Принятое направление:

- добавить предельный возраст разведки;
- просроченные данные не использовать для автоматического плана;
- возраст показывать пользователю;
- точное значение лимита оформить настраиваемым, без жёсткой продуктовой фиксации в этом аудите.

### A8. Привязка к конкретной вкладке Nemexia

При нескольких вкладках бот должен работать с явно выбранной вкладкой, а не с первой найденной.

Требуемое поведение:

- команда «Привязать текущую вкладку»;
- сохранение CDP target ID на время сессии;
- отображение заголовка/URL привязанной вкладки;
- при закрытии или потере вкладки операция останавливается;
- молчаливое переключение на другую вкладку запрещено.

## 2. Не принимается в работу

Следующие рекомендации аудита отклонены владельцем и не должны автоматически попадать в implementation roadmap:

1. удаление `saved_pages` и реальных целей из публичного GitHub;
2. изменение алгоритма приоритета целей с текущей сортировки по металлу;
3. отдельная переработка числового парсера;
4. защита ZIP-распаковки как самостоятельная задача;
5. превращение жёстко заданных параметров аккаунта/расы в универсальный `GameProfile`;
6. удаление runtime monkey patch как отдельная задача;
7. обязательное внедрение CI, mypy/pyright и новой системы тестов в рамках этого цикла;
8. формальная система версий и миграций SQLite;
9. крупное разбиение монолитных модулей;
10. удаление или возврат влияния устаревших настроек;
11. предложения UI/UX-аудита: перекраска кнопок, перестройка навигации, новые экраны, таблицы, вкладки настроек и DPI-редизайн.

Это не утверждение, что перечисленные наблюдения технически неверны. Это осознанное решение не тратить на них время в текущем проектном цикле.

## 3. Итоговый обязательный scope

Implementation-работы после merge audit PR должны быть ограничены следующими блоками:

1. `RAID-VERIFICATION-AND-RESPONSE-GATE`
   - явный положительный `pass`;
   - обязательная новая строка полёта;
   - состояние `unverified`;
   - запрет снятия `disabled`.

2. `ALL-FLIGHT-SLOT-ACCOUNTING`
   - учёт всех миссий при расчёте свободных слотов.

3. `FLIGHT-TIME-PROVENANCE`
   - проверка формулы восстановления `sent_at`;
   - маркировка вычисленного времени.

4. `REPORT-TIMEZONE-AND-FRESHNESS`
   - часовой пояс сервера;
   - предельный возраст разведки.

5. `BOUND-NEMEXIA-TAB`
   - явная привязка к конкретной вкладке.

Любые дополнительные задачи требуют нового явного решения владельца.

## 4. Порядок выполнения

Рекомендуемый порядок:

```text
1. RAID-VERIFICATION-AND-RESPONSE-GATE
2. ALL-FLIGHT-SLOT-ACCOUNTING
3. REPORT-TIMEZONE-AND-FRESHNESS
4. FLIGHT-TIME-PROVENANCE
5. BOUND-NEMEXIA-TAB
```

Первые два блока напрямую влияют на безопасность реальных отправок и должны выполняться раньше остальных.
