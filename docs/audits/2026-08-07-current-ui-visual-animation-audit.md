# Полный визуальный аудит Nemexia Raid Manager

Baseline: `2f3ea9a3be6a14bd0a3c216d6ae7c83444f192fa`  
Дата: 2026-08-07  
Формат: статический аудит текущего Tkinter UI после добавления экрана «Обломки» и фоновой работы браузера.

## 0. Граница аудита

Этот документ касается только presentation layer:

- визуальная иерархия;
- структура блоков внутри существующих экранов;
- цвета;
- шрифты;
- размеры;
- отступы;
- таблицы;
- кнопки;
- поля ввода;
- статусы;
- иконки;
- hover/focus/pressed states;
- анимации и микроинтеракции;
- DPI/responsive-поведение;
- визуальная консистентность диалогов и логов.

Не предлагается менять:

- алгоритмы рейдов;
- расчёты астероидов;
- сортировку целей;
- состав данных;
- браузерную автоматизацию;
- обработчики `command`;
- существующие `bind`-сценарии;
- базу SQLite;
- сетевые действия;
- правила отправки и подтверждения;
- автоматические режимы как бизнес-логику.

Допустима только перестановка уже существующих элементов по блокам и изменение их оформления.

Pixel-perfect снимок работающего Windows-приложения в рамках этого аудита не снимался. Выводы основаны на актуальной разметке `app.py`, `app_entry.py` и `debris_asteroids_feature.py`. Перед реализацией визуального патча нужен отдельный screenshot pass на Windows 100/125/150% DPI.

# 1. Краткий вывод

Текущий интерфейс уже имеет хороший базовый dark-command-center стиль и не выглядит как стандартный Tkinter по умолчанию. Проблема не в выбранной эстетике, а в отсутствии законченной дизайн-системы.

Сейчас UI визуально находится примерно в состоянии **«рабочий инженерный инструмент, поверх которого уже нанесена тема»**. Следующий шаг — сделать из него **цельный desktop control panel**, не меняя функциональность.

Главные визуальные проблемы:

1. слишком много элементов имеют одинаковый визуальный вес;
2. экраны с большим числом действий превращаются в длинную горизонтальную полосу кнопок;
3. таблицы являются главным носителем информации, но не используют семантическое выравнивание, иерархию колонок и горизонтальный скролл;
4. экран «Астероиды» и новый экран «Обломки» функционально понятны, но визуально перегружены контролами и метриками;
5. настройки выглядят как одна длинная системная форма вместо нескольких смысловых групп;
6. Unicode-иконки в sidebar неоднородны по форме и оптической ширине;
7. типографика логична, но задаётся вручную десятками отдельных значений;
8. реальные анимации практически отсутствуют: состояния меняются мгновенно;
9. несколько цветов статусов и таблиц заданы локальными hex-значениями, а не через общие design tokens;
10. минимальное окно `1120×680` слишком близко к пределу для текущей плотности контролов.

Визуальный редизайн можно сделать **без изменения функциональности**.

Это хороший фундамент. Не нужен полный recolor приложения.

## 2.2. Постоянная левая навигация

Sidebar — правильная модель для приложения, в котором много рабочих экранов. Пользователь всегда понимает, где он находится.

## 2.3. Header + статус браузера

Текущий topbar уже содержит:

- заголовок страницы;
- состояние браузера;

- кнопку сохранения страницы из `app_entry.py`.

Сам паттерн правильный. Нужна только более чистая визуальная композиция.

## 2.4. Карточки KPI

Карточки на dashboard и asteroids хорошо отделяют короткие показатели от таблиц. Этот паттерн стоит расширять и унифицировать.

Уже существуют:

- `primary`;
- `success`;
- `danger`;
- `secondary`;

Это почти готовая компонентная система. Нужно только поправить смысл цветов и состояния.

## 2.6. Единый Treeview style

Таблицы используют общий `Dark.Treeview`, общую высоту строки и общую шапку. Это сильная база для дальнейшей полировки.

# 3. Целевой визуальный характер

Предлагаемый стиль можно условно назвать **Orbital Command 2.0**.

Он должен быть:

- тёмным;
- строгим;
- технологичным;
- плотным, но не тесным;
- без декоративной «игровой» перегрузки;
- с ощущением рабочего командного центра;
- с ясной иерархией: экран → блок → значение → действие;
- с минимальным количеством визуального шума.

Не стоит делать:

- неоновые glow-эффекты по всему окну;
- градиенты на каждой кнопке;
- псевдо-3D;
- большое количество анимированных элементов;
- разноцветные карточки;
- закругления ради закруглений;
- попытку превратить стандартный Tkinter в веб-интерфейс любой ценой.

Для Tkinter лучше использовать сильную геометрию, аккуратные линии, состояние цвета и хороший spacing.

# 4. Design tokens

Сейчас часть токенов уже существует, но размеры и локальные цвета разбросаны по коду.

## 4.1. Цветовые уровни

Оставить текущую палитру и формализовать уровни:

```text
surface-0    #080d16   основной фон
surface-1    #0b1220   sidebar
surface-2    #101a2a   основные панели
surface-3    #17243a   raised / input / selected nav
border-1     #24334a
border-focus #4f8cff
text-1       #f1f6ff
text-2       #aab8ca   вторичный текст
text-3       #74869c   подписи/metadata
accent       #4f8cff
accent-hover #78a7ff
success      #4ed69a
warning      #ffc15a
error        #ff7180
```

`MUTED #93a4ba` можно оставить, но нужно исключить множество локальных близких серых (`#6f829a`, `#536174`, `#77869a`, `#6a7686`, `#56606e`) либо превратить их в 2–3 именованных уровня.

## 4.2. Семантические поверхности

Для строк таблиц и badges вместо локальных hex:

```text
success-bg   глубокий зелёно-синий
warning-bg   глубокий янтарный
error-bg     глубокий бордовый
info-bg      глубокий синий
selected-bg  BLUE_DARK
```

Это позволит одному и тому же статусу выглядеть одинаково во всех разделах.

## 4.3. Spacing scale

Ввести единый ритм:

```text
4   xs
8   sm
12  md
16  lg
24  xl
32  2xl
```

Сейчас используются `3`, `5`, `6`, `7`, `8`, `10`, `14`, `16`, `18`, `20`, `22`, `26`, `28` px. Интерфейс от этого не ломается, но визуально элементы чуть «плывут» относительно друг друга.

## 4.4. Контуры

Использовать один стандарт:

- 1 px border для panel/card/input;
- 2 px только для keyboard focus / critical state;
- не использовать дополнительные рамки внутри таблицы без необходимости.

# 5. Типографика

## 5.1. Текущее состояние

Используются:

- `Segoe UI`;
- `Segoe UI Semibold`;
- `Consolas` для логов.

Диапазон размеров примерно 8–24 pt.

Шрифтовое направление правильное для Windows desktop. Семейство менять не нужно.

## 5.2. Проблема

Каждый widget сам задаёт font tuple. Из-за этого масштаб и жирность визуально похожих элементов иногда отличаются.

## 5.3. Рекомендуемая шкала

Создать named Tk fonts:

```text
Display       Segoe UI Semibold 24
PageTitle     Segoe UI Semibold 20
SectionTitle  Segoe UI Semibold 12
Metric        Segoe UI Semibold 24–28
BodyStrong    Segoe UI Semibold 9–10
Body          Segoe UI 9–10
Caption       Segoe UI 8–9
Mono          Consolas 9
```

Главное — не размер сам по себе, а единое назначение.

## 5.4. Заголовки

Текущий page title `22` выглядит нормально, но section title `12` + subtitle `9`, стоящие на одной горизонтальной линии, иногда делают header слишком длинным.

Лучше:

```text
Заголовок секции
Короткое пояснение на следующей строке
```

Это особенно полезно на экранах астероидов, очереди и обломков.

## 5.5. Числа

Для KPI и таймеров желательно использовать tabular/равномерное визуальное поведение. Segoe UI не всегда идеально воспринимается при постоянно меняющихся countdown.

Варианты:

- оставить Segoe UI для KPI;
- использовать Consolas только для быстро меняющихся технических таймеров;
- не использовать monospace для всей таблицы.

# 6. Sidebar

## 6.1. Текущее состояние

Ширина `232 px`, сверху бренд, далее полный список экранов, снизу две кнопки браузера.

После добавления «Обломков» пунктов стало ещё больше.

Навигация использует символы:

```text
⌂ ≡ ◷ ◉ ◆ ◇ ◎ ↺ ⚙ ≣
```

## 6.2. Проблемы

1. Unicode-иконки имеют разную оптическую ширину и baseline.
2. Выбранный пункт выделяется большой прямоугольной заливкой `PANEL_ALT`; этого достаточно функционально, но выглядит тяжеловато.
3. Все пункты находятся в одной группе и имеют одинаковый вес.
4. Нижние действия «Запустить браузер» / «Подключиться» визуально конкурируют с навигацией.

## 6.3. Рекомендация

Не менять маршруты страниц, а только сгруппировать визуально:

```text
ОБЗОР
Дашборд

ОПЕРАЦИИ
План отправки
Активные
Астероиды
Обломки

ДАННЫЕ
Разведка
Цели
История

СИСТЕМА
Настройки
Лог
```

Групповые заголовки — Caption uppercase, низкий контраст.

Активный пункт:

- `surface-3` либо даже фон sidebar;
- яркий текст;
- 3 px accent rail слева;
- иконка акцентная;
- без сильной массивной заливки.

## 6.4. Иконки

Лучший вариант — единый набор 16×16 monochrome PNG, поставляемый вместе с приложением.

Если не хочется добавлять ассеты, лучше использовать либо текст без иконок, либо ограниченный согласованный набор символов. Текущая смесь псевдографики визуально дешевле, чем остальная тема.

# 7. Верхняя панель

## 7.1. Текущее состояние

Слева большой page title, справа status badge, `Синхронизировать`, затем внедрённая кнопка `Сохранить страницу`.

## 7.2. Проблема

Справа постепенно растёт набор системных действий, и topbar начинает превращаться в toolbar.

## 7.3. Рекомендация

Разделить визуально на три зоны:

```text
[Название раздела]                     [● Браузер подключён] [↻] [Диагностика]
```

- status сделать компактным pill/badge;
- `Синхронизировать` визуально сократить до secondary compact button;
- `Сохранить страницу` воспринимать как диагностику, а не равноправное основное действие;
- сохранить текущие callbacks без изменений.

Высота topbar должна быть стабильной на всех страницах.

# 8. Кнопки

## 8.1. Сильная сторона

`make_button()` уже централизует большую часть кнопок.

## 8.2. Что мешает

- `success` зелёный используется в том числе для действия «Отправить»;
- одновременно на странице может быть 5–9 кнопок одинаковой высоты;
- длинные toolbars перестают помещаться при меньшей ширине;
- нет отдельного компактного размера;
- `activebackground` меняется мгновенно, реальной motion-системы нет;
- disabled-state визуально не стандартизирован.

## 8.3. Визуальная семантика

Предлагается:

```text
Primary blue   основное безопасное действие экрана
Secondary      вспомогательное действие
Warning/amber  действие, которое реально отправляет флот
Danger/red     удалить / остановить
Ghost          навигация, move up/down, tertiary
Success/green  в первую очередь статус результата, а не кнопка отправки
```

Это только цветовая семантика; callback кнопок не меняется.

## 8.4. Размеры

Два стандарта:

```text
regular:  высота около 36–38 px
compact:  высота около 30–32 px
```

Toolbar может использовать compact, ключевая CTA — regular.

## 8.5. Hover / pressed / focus

Для каждой кнопки нужны четыре состояния:

- default;
- hover;
- pressed;
- keyboard focus.

Focus ring должен быть заметнее текущего `highlightthickness=1`.

# 9. Анимации и motion system

## 9.1. Текущее состояние

Настоящих анимаций почти нет.

Есть только мгновенные изменения:

- `activebackground`;
- смена цвета выбранной навигации;
- изменение badge `АВТО ВКЛ/ВЫКЛ`;
- мгновенное `tkraise()` страниц;
- мгновенная перерисовка KPI и таблиц;
- обычные modal messagebox.

Это делает UI быстрым, но немного «механическим».

## 9.2. Главный принцип

Не нужно превращать операторское приложение в анимированную панель.

Motion должен объяснять изменение состояния, а не украшать интерфейс.

## 9.3. Рекомендуемые микроанимации

### Hover

80–120 ms мягкого перехода цвета кнопки/навигации.

В Tkinter это можно реализовать небольшим color interpolation через `after()`. Не анимировать размеры.

### Selected navigation

При смене раздела можно анимировать только accent rail 100–140 ms либо оставить мгновенную смену. Полный slide страницы не нужен.

### KPI update

Когда значение карточки меняется:

- короткий `surface highlight` 150–200 ms;
- без count-up animation.

Это помогает заметить, что данные обновились.

### Busy state

Для долгих операций:

```text
Сканирование ···
Сканирование •··
Сканирование ·•·
Сканирование ··•
```

или маленький indeterminate progress bar.

Это лучше, чем постоянная декоративная spinner-анимация.

### Success/Error

После завершения действия строка или badge может получить мягкий flash 200–300 ms и перейти в постоянный semantic color.

## 9.4. Что не делать

- fade всего окна;
- масштабирование кнопок;
- slide таблиц;
- бесконечное свечение AUTO badge;
- анимированный фон;
- motion внутри больших Treeview на каждом timer tick.

## 9.5. Ограничение производительности

Tkinter animation должна работать через `after()`, без `sleep()` в UI thread.

Цель — не 60 FPS. Для цветовых переходов достаточно 20–30 FPS и длительности до 200 ms.

# 10. Карточки

Карточки имеют:

- border;
- title 9 semibold;
- metric 24 semibold;
- subtitle 8;
- одинаковую структуру.

## 10.2. Что улучшить

1. Уменьшить количество uppercase там, где это не KPI.
2. Сделать subtitle чуть контрастнее текущего локального `#6f829a`.

Четыре карточки выглядят логично. Визуально стоит сделать:

- одинаковую внутреннюю высоту;
- число/таймер главным;
- subtitle одной строкой;
- мягкий status accent только там, где действительно есть состояние.

# 11. Таблицы

Это самая важная визуальная зона приложения.

## 11.1. Текущее состояние

Общий Treeview:

- `rowheight=40`;
- все колонки `anchor="center"`;
- header semibold 9;
- vertical scrollbar;
- sorting по клику header;
- selected background `BLUE_DARK`.

## 11.2. Главные проблемы

### Все данные центрированы

Центрирование подходит координатам и коротким статусам, но хуже читается для:

- игроков;
- заметок;
- ошибок;
- длинных текстов;
- числовых столбцов.

Рекомендация:

```text
text       left
notes      left
errors     left
coords     center
status     center/left
numbers    right
time       center
```

### Нет горизонтального scrollbar

Queue и Targets физически шире окна. Это визуальный дефект, особенно на 125–150% DPI.

Добавление horizontal scrollbar не меняет функциональность и должно входить в первый visual patch.

### Слишком много равноправных колонок

Даже если оставить весь набор, ключевые колонки должны визуально иметь больший вес:

- Координаты;
- Металл;
- Время;
- Статус.

Вторичные значения можно сделать немного более muted через tag/row presentation либо меньшую ширину.

### Сортировка не имеет индикатора

После клика пользователь не видит направление sort. В header желательно показывать `▲ / ▼`.

Это визуальный feedback существующей функции сортировки.

## 11.3. Row states

Сейчас состояния используют локальные цвета (`#15312a`, `#44212a`, `#1b315d`). Их нужно унифицировать через semantic tokens.

Лучше не окрашивать всю строку ярко. Использовать очень тёмную подложку + цветной status text или небольшой marker.

## 11.4. Hover row

Лёгкий hover помогает работать с широкими таблицами. Он должен быть едва заметнее panel background.

Это самый перегруженный toolbar.

Сейчас одновременно видны:

# 24. Responsive и Windows DPI

Текущие размеры:

```text
initial   1360×820
minimum   1120×680
sidebar   232 px
```

## Риски

- на 1366×768 приложение почти равно экрану;
- 125% scaling делает фактическое пространство заметно меньше;
- длинные toolbars могут обрезаться;
- settings не имеют scroll;
- wide Treeview не имеют horizontal scroll;
- 5 asteroid cards слишком плотные.

## Минимальная матрица визуальной проверки

| Resolution | Scale | Что проверять |
|---|---:|---|
| 1366×768 | 100% | минимальная высота и toolbars |
| 1920×1080 | 100% | основной layout |
| 1920×1080 | 125% | типичный Windows DPI |
| 2560×1440 | 150% | плотность карточек/шрифтов |
| 3840×2160 | 200% | масштаб и читаемость |

## Правила адаптации

Без изменения функциональности можно:

- переносить toolbar на вторую строку;
- перестраивать KPI grid `5 → 3+2`;
- добавлять scroll containers;
- позволять таблицам растягиваться;
- сохранять sidebar фиксированным либо уменьшить его до ~210 px на компактной ширине.

# 25. Accessibility / визуальная читаемость

3. warning/error text должен иметь достаточный контраст;

6. danger button всегда визуально отделён от обычных действий;
7. checkbox state должен быть читаем без угадывания символа.

# 29. Критерий готового визуала

Интерфейс можно считать визуально завершённым, когда:

- все экраны выглядят как части одной системы;
- пользователь за 1–2 секунды понимает главный блок страницы;
- primary / send / stop / delete визуально различаются;
- ни одна страница не выглядит как «полоса из 10 кнопок»;
- поля имеют одинаковую высоту и focus state;
- таблицы читаются без угадывания, к какой колонке относится число;
- wide tables доступны через horizontal scroll;
- status colors одинаковы во всех разделах;
- sidebar не выглядит собранием разноразмерных Unicode-символов;
- settings имеют смысловые группы;
- обычные астероиды и обломки выглядят родственными экранами;
- анимации помогают видеть изменение состояния, но никогда не мешают скорости работы;
- приложение нормально выглядит на 100%, 125% и 150% Windows scaling;
- ни один visual patch не изменил фактическую работу автоматизации.

# 30. Итоговая рекомендация

Не нужен новый дизайн с нуля.

Нужно сохранить текущий dark-space visual language и выполнить системную полировку:

```text
токены → типографика → компоненты → группировка экранов → таблицы/DPI → motion
```

Самый большой прирост качества даст не анимация, а первые три вещи:

1. единая компонентная система;
2. более сильная группировка кнопок/настроек;
3. профессиональная работа с широкими таблицами.

После этого небольшая motion-система сделает приложение живее без ощущения веб-сайта или игры внутри игры.
